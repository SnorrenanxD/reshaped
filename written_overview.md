# Written overview AI use case - Reshaped x Rénan
## What I built
An LLM-powered guided workflow chat interface, with responses grounded in the VIMS marine operations safety management manual. 

## The user problem it adresses
With hundreds of pages and tens of sections, this solution enables marine personell to quickly find the next critical steps during malfunctions, near misses, incident reporting etc. Instead of scrolling through the SMS, the user instantly knows which steps they have to take, while the interface can also provide the full document text when needed for peace of mind.

## How it works
Before starting the application, the case manual is processed in the `src/ingest.py` script. The raw pdf file is turned into chunks corresponding to all the sections in the SMS, and is stored as a JSON file.

When the application is launched using Streamlit the user is presented with a locally hosted GUI webpage in `app.py`. This UI renders graphical element using the structured output generated by the LLM.

When the user submits a query to the LLM, the query is managed in `src/router.py`. This is where the exact path of the input and output is handled, including a system prompt and schemas for the structured outputs.

## Key design decisions and trade-offs
- Section-based chunking.
  - I implemented section-based chunking in favor of agnostic size-based chunking when ingesting the PDF file to make retrieval simpler and more accurate, so leakage of other sections will not be an issue for generating responses. This increases complexity with intricate regex but as this was made with AI assistance, the complicated regex was working quickly.
- LLM-based section retrieval on titles.
  - At first I tried a more traditional RAG approach by using sentence transformers semantic matching combined with BM25 for retrieval, with the LLM only generating the response. I quickly found out that the BM25 search scores common but irrelevant words too highly, and that semantic matching is overconfident on similar words of which the context changes their meaning. Since summarizing context is exactly the sort of task that LLMs are proficient in, switching to LLM-based retrieval yielded much better results, although it did increase the amount of calls.
- Verbatim section shown alongside answer.
  - While the goal of the assignment is to provide quick and accurate answers to personell from the dry manual, hallucination can always be an issue. As some situations or responses might raise trust issues with the system, the original undoctored section is also provided to the user, so a human check in a safety critical process can always be guarded.
- Guided workflow UI through chat interface.
  - While interacting with LLMs is most often done through chat interfaces, this specific problem raises the need for a user interface that perfectly aligns with the responses a user might want to receive. By letting the LLM return structured output, we can render a guided workflow with tick-able elements to clearly and plainly communicate exactly what the course of actions should be given a situation, according to the SMS. Using only chat messages would also work, but would limit the ease of use and increase cognitive load by having to reread message or remember which steps are done.
- Verify before generation for ambiguous matches, not for high confidence.
  - The sections retrieved by the LLM are not always identical for similar inputs. To reduce the amount of false positives, verification is done by asking the LLM again if the section it selected actually provides an answer to the user's query. This requires another call to the LLM, which can be slow and/or expensive. So to maintain a feeling of swiftness, verification is only done in cases where the LLM is not confident in its response.
- Cloud model with local backup.
  - While originally this implementation started from an unchecked assumption (on sea there will likely be a bad connection), after asking it turned out that a stable internet connection could be assumed after all. While removing the offline local backup would improve simplicity as it does not serve an immediate purpose now, I opted to maintain it for my own insurance, as a sketchy internet connection during the demo would be a death sentence.
- No vector database.
  - While RAG also sometimes uses a vectorized database, it was simply not needed for our purpose. This would only significantly increase the complexity of our implementation while the document is short enough (only 87 section including the appendices) for the LLM to quickly read all titles and save them as context when selecting which sections will be used to generate a response.
